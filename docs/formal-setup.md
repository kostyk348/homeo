# Формальная постановка: homeo как стохастическая релаксация над инвариантами

Этот документ фиксирует математическую постановку валидационного апгрейда
(аудит 2026‑11): что считается состоянием, что — допустимым множеством, что
именно делает ядро `homeo/engine.py`, чем являются барьерные шарниры и
safety‑фильтр, и какой исследовательский вопрос проверяет валидационный стенд.
Численные результаты — в `docs/validation.md` и `results/*.json`.

---

## 1. Объект и состояние

Валидационный объект — два связанных резервуара (`homeo/control.py`,
`TwoTankPlant`). Состояние — вектор уровней:

```
x = (h1, h2) ∈ ℝ²,   h1, h2 ≥ 0
```

Динамика (явный Эйлер с шагом `dt`):

```
A1·h1' = u − q12(h1, h2)
A2·h2' = q12(h1, h2) − qout(h2) − d
```

где `u` — расход насоса в бак 1 (управление, физически ограничено
`u ∈ [0, umax]` — насыщение привода), `d` — расход потребителя из бака 2
(неизвестное контроллеру возмущение). Перетоки — линейные (`q12 = c12·(h1−h2)`,
`qout = c2·h2`) на «линейном стенде» и квадратичные (`q12 = k12·sign(Δ)·√|Δ|`,
`qout = k2·√h2`) в демо‑кейсе. Параметры объекта могут дрейфовать во времени
(робастностный протокол), а номинальная модель контроллера может быть смещена
относительно объекта (демо‑кейс).

Контроллер видит зашумлённые измерения `y = x + noise`, `noise ~ N(0, σ²I)`,
и не видит ни текущее `d`, ни истинные параметры объекта.

## 2. Допустимое множество Ω

Допустимое множество — в общем виде аудита:

```
Ω = { x : g_j(x) ≤ 0, j = 1..m;   h_i(x) = 0, i = 1..p }
```

В валидационных сценариях `Ω` задаётся четырьмя неравенствами‑полосами
уровней (`Scenario.g_funcs`):

```
g1(x) = lo1 − h1        g2(x) = h1 − hi1
g3(x) = lo2 − h2        g4(x) = h2 − hi2
```

Ограничения‑равенства `h_i` в сценариях пусты (`p = 0`), но формализм и
`safety.max_violation` их поддерживают: мера нарушения

```
viol(x) = max( max_j g_j(x), max_i |h_i(x)| − 2·tol )  ⊖  tol
```

обрезается к нулю внутри Ω (`homeo/safety.py::max_violation`), т.е.
`viol(x) = 0 ⇔ x ∈ Ω` с запасом `tol`.

## 3. Что делает ядро: релаксация в пространстве политики

Ядро `homeo/engine.py` — не решатель ОДУ и не планировщик траектории, а
**стохастическая релаксация в пространстве политики**. Нормированные
координаты `X ∈ [−1,1]^n` разворачиваются в физическое управление
(`n = 1`, `u = (X+1)·umax/2`). Поведение задаётся набором конкурирующих
инвариантов `I_j(X)` с весами `w_j(X)`, а контроллер каждый тик решает задачу

```
E(X) = Σ_j w_j(X) · |I_j(X)|^{p_j}   →   min_X ∈ [−1,1]^n
```

методом:

* **Adam** по численному градиенту (центральные разности — автоматически
  учитывается `dW/dX`, т.е. «само‑вес» инвариантов);
* **термальный шум CLT**: к каждому шагу добавляется `(12·U − 6)·T`, где
  `U ~ Uniform(0,1)` — сумма двенадцати равномерных; по ЦПТ это `N(0,1)`;
* **annealing**: температура затухает по закону `T_t = T0·2^(−k·t)`, так что
  шум помогает выбраться из мелких локальных ям только в начале релаксации;
* **проекция на бокс** `[−1,1]^n` после каждого шага (флаг `project`) — это
  единственная «жёсткая» операция ядра, и она про бокс координат политики,
  а не про Ω;
* каждый тик контроллера — **свежая релаксация** (сброс моментов Adam, тёплый
  старт от предыдущего управления), т.е. контроллер — это «пере‑балансировка
  инвариантов под текущее состояние», а не обученная политика.

Ключевая особенность контура (`HomeoTankController`): инварианты оценивают
**последствия политики**, а не только текущее измерение. Инварианты строятся
на предсказанной траектории уровней при постоянном кандидате `u` на горизонте
`H` шагов номинальной модели (без возмущений, с оценённым расходом
потребителя `d_hat`):

* **цель**: средний уровень бака 2 на второй половине горизонта должен быть
  равен уставке — `(h2_bar − ref)/scale2`, вес `w_goal`;
* **барьерные шарниры**: максимальная по траектории глубина выхода за каждую
  полосу, делённая на ширину полосы, вес `w_safe` — см. §4;
* **экономия**: `(u − u_prev)/umax`, вес `w_eff` — штраф за дёргание привода.

Предсказание при постоянном `u` — сознательно простое (это не MPC с
оптимизацией траектории): релаксация ищет компромисс между инвариантами в
одномерном пространстве управления.

## 4. Барьерные шарниры (barrier hinges)

Полосы Ω входят в энергию как **односторонние шарнирные штрафы**:

```
hinge_j(u) = max(0, max по траектории предсказания глубины выхода за полосу j)
```

Шарнир равен нулю строго внутри допустимой области — его градиент не толкает
политику, пока прогноз остаётся в Ω, и растёт линейно по глубине нарушения,
как только прогноз выходит за границу. Это «барьероподобное» поведение
(soft barrier): в отличие от точного барьерного метода штраф конечен, и
никакой гарантии невыхода он не даёт — только давлению веса `w_safe = 25`
против `w_goal = 1`.

Две инженерные детали, зафиксированные валидацией:

* **запас `safety_margin`**: шарнир держит траекторию не на границе, а на
  `margin` глубже (0.02–0.03 м). Без запаса минимизатор шарнира «дребезжит»
  вокруг границы, потому что строго внутри градиент нулевой;
* **оценка возмущения `d_hat`**: расход потребителя оценивается из баланса
  бака 2 (`d ≈ q12 − qout − dh2/dt`) со сглаживанием первого порядка; оценка
  впитывает и параметрическое смещение модели, давая контуру
  интегралоподобное поведение при постоянном возмущении.

## 5. Safety‑фильтр (проекция кандидата на допустимые управления)

Второй, независимый от энергии механизм — **проекционный safety‑фильтр**
(`homeo/safety.py::filter_control`). Он не меняет ядро: кандидат `u_cand` от
любого контроллера проходит проверку перед подачей на привод:

1. на номинальной модели от текущего измеренного состояния прогнозируется
   траектория на `horizon` шагов при **worst‑case** возмущении
   `d = d_bound` (известная верхняя граница расхода потребителя);
2. по сетке `n_grid` точек на `[0, umax]` (плюс сам кандидат) считается
   `viol` предсказанной траектории;
3. из допустимых (`viol ≤ tol`) выбирается **ближайший к кандидату** — это и
   есть проекция кандидата на множество допустимых управлений;
4. если допустимых нет — возвращается best‑effort управление с минимальным
   предсказанным нарушением, и событие помечается `feasible_found = false`;
5. каждое срабатывание (`u_out ≠ u_cand`) логируется — счётчик триггеров
   входит в результаты.

Важно: фильтр **сеточный и одномерный** (скалярное управление), его
«проекция» — ближайшая точка сетки, а гарантию он даёт только относительно
номинальной модели с консервативным `d_bound`, не относительно реального
объекта. Это не CBF‑фильтр с доказательствами и не точная проекция на Ω.

## 6. Исследовательский вопрос

Стенд построен вокруг вопроса:

> **Что именно обеспечивает безопасность — стохастическая релаксация над
> инвариантами (мягкие барьеры в энергии) или внешняя гарантия
> (фильтр с проекцией)?**

Или в терминах аудита: *стохастическая релаксация vs гарантированная
инвариантность*. Архитектурно это два разных слоя:

| слой | механизм | гарантия |
|---|---|---|
| ядро + барьерные шарниры | мягкие штрафы в `E`, вес `w_safe` | нет (штраф конечен) |
| safety‑фильтр | проекция кандидата на сетке допустимых | только на модели |

Валидация отвечает на вопрос эмпирически (см. `docs/validation.md`): бейзлайны
ПИД/LQR — «релаксации нет и инвариантности нет», `homeo` без safety‑инвариантов
+ фильтр — «фильтр без релаксации», полная конфигурация — «оба слоя».

## 7. Честные ограничения (что здесь НЕ доказано и НЕ реализовано)

1. **Нет функции Ляпунова.** Устойчивость замкнутого контура не доказана
   ни аналитически, ни численно; `settling_time`/`recovery_time` — эмпирические
   метрики на конкретных сценариях, не оценки сходимости.
2. **Нет проекции на Ω и нет инвариантности.** Ни релаксация, ни барьерные
   шарниры не гарантируют `x(t) ∈ Ω`: штрафы мягкие, между тиками состояние
   может выйти из Ω, а при больших возмущениях — выходит (развёртка
   амплитуды в `results/robustness.json`). Единственный механизм с
   «гарантийной» природой — сеточный фильтр, и тот даёт гарантию лишь
   относительно номинальной модели и известной границы `d_bound`.
3. **Фильтр — сеточный и одномерный.** Точность проекции ограничена сеткой
   (`n_grid = 41`), поддерживается только скалярное управление; для вектора
   управлений требуется другой алгоритм.
4. **Предсказание — при постоянном `u` на горизонте.** Это не MPC: внутри
   горизонта политика не переоптимизируется, возмущение в прогнозе —
   константа (`d_hat` у контроллера, worst‑case `d_bound` у фильтра).
5. **Метод локальный.** Adam + термальный шум находят локальный минимум
   `E`; при сильно невыпуклой сумме инвариантов результат зависит от тёплого
   старта, глобальный минимум не гарантирован.
6. **Валидация — симуляция.** Все выводы относятся к двум смоделированным
   объектам (линейный стенд, квадратичные перетоки) с фиксированными
   seed'ами; на реальную установку они переносятся только как гипотезы.
